# Control-plane HTTP budgets

Every runner HTTP call to the control plane has its own fixed timeout; there are no client-side retries. Heartbeats, the stopped acknowledgement, event batches, artifact uploads and downloads, completion, and profile requests all use the PHP-compatible 5-second budget. The claim endpoint alone uses a 30-second budget, since a claim request builds the run manifest server-side (selecting queued work, allocating the attempt and fence, and assembling the charter and workspace references), which is slower than the fixed-shape requests the 5-second budget covers.

When an HTTP call's own budget elapses, the runner reports it distinctly from the attempt passing its deadline: `Runner request to <endpoint> exceeded its <budget> budget before a response was received.` This is deliberately different wording from `Runner attempt passed its deadline before a result could be reported.`, which is reserved for the claimed attempt's own deadline (`claim.Deadline`, enforced by the lease guard's context) expiring — a genuinely different condition an operator should not have to disambiguate from a slow request. The distinction is structural, not string matching: every request runs under a context derived from the caller's with the client's budget, and a budget-exceeded condition is reported only when that derived context expired while the caller's context was still live. If the caller's context had already expired (for example because the attempt's deadline fired first), the error still reads as the attempt passing its deadline, and a deadline error the transport returns on its own, before any budget elapsed, passes through unchanged. This is why no call site wraps a client call in a second timeout equal to the client's own budget: a caller deadline of the same size would race the client's and could win, misreporting a genuine budget timeout as the caller's deadline instead. The lease guard's heartbeat and completion calls, the supervisor's stopped acknowledgement on a claim-persist failure, and `run --discard-attempt`'s best-effort acknowledgement all pass their own caller context through unwrapped, the same way. The supervisor's recovery `reconcile` and `cleanup` windows do wrap a timeout of their own (the 90-second `cleanupTimeout`), but that window is deliberately much larger than any client budget, so the budget still fires first and the same classification holds.

This wording also flows into the runner event log's `claim_failed` event `error` field (see [runner event log](logging.md)) for a claim call specifically, since claims are logged on failure. `<endpoint>` is the request path only, never a host or query string; for an in-attempt call (heartbeat, stopped acknowledgement, event batch, completion) it embeds the attempt's own ULID, for example `/runner/v1/attempts/<id>/completion`.

Because no call site adds its own timeout, every `supervisor.Client` implementation must bound each call under its own budget and honour the passed context: `renew` holds the lease guard's mutex for the duration of the call, and `stop` blocks on the guard's goroutine exiting, so a call that ignored its context could stall both indefinitely.
