# Runner event log

The installed `shipmunk-runner` (fixture and Codex drivers alike) writes a structured event log at `<state-dir>/logs/runner.log`, next to the attempt journal it already keeps under `<state-dir>`. Each line is one self-contained JSON object, so the file can be tailed or parsed with `jq` without buffering: `tail -f <state-dir>/logs/runner.log | jq .`. Every record carries `time` (RFC 3339, UTC) and `event`, plus event-specific fields such as `run_id`, `attempt_id`, `fence`, `outcome`, `reason`, `container_id`, or `step`.

The log covers the whole supervised lifecycle of one attempt: `claim` when a claim is accepted (with its identity and deadline), `claim_empty` or `claim_failed` when none is returned or the request itself fails, `workspace_prepare_start`/`workspace_prepare_done`/`workspace_prepare_failed` around downloading and staging the workspace, `sandbox_create_started`/`sandbox_created`/`sandbox_exit` (with the container ID and exit code) or `executor_exit`/`executor_failed` for the Codex composite executor, `classified_failure` with the runner- or provider-classified `reason` (for example `malformed_output`, `missing_result`, `invalid_result`, `auth_expired`, `rate_limited`) whenever an attempt ends in a classified failure rather than a Go error, `heartbeat`/`heartbeat_failed`/`heartbeat_stop` for lease renewal, `cleanup_start`/`cleanup_done`/`cleanup_failed` (with the failing `step`: executor, sandbox, watchdog, workspace, acknowledge, or state_clear) for sandbox and journal teardown, and `result_delivered` once the server has accepted the attempt's result. A setup failure before supervision starts (an unreadable token, a missing Docker engine, an unpinned image, and similarly) is recorded as `setup_failed` with the failing `step`.

Every message the runner prints to stderr for a condition it cannot fully classify — for example `Runner setup failed. ...` or `Runner stopped before a completed result could be reported. ...` — ends with `Check the runner log for the recorded condition: <path>`, naming this same file so an operator never has to guess where the detail landed. Conditions the runner can classify (an expired lease, a revoked attempt, a control-plane HTTP error, an HTTP call's own budget elapsing, the application refusing the stopped acknowledgement) still get their own specific stderr sentence in addition to the log pointer. An HTTP call's own budget elapsing (`Runner request to <endpoint> exceeded its <budget> budget before a response was received.`) is reported distinctly from the attempt's own deadline expiring; see [control-plane HTTP budgets](http-budgets.md) for the per-endpoint budgets, including the claim endpoint's larger one, and for the `claim_failed` event's `error` field carrying this same wording.

The log is designed to never carry secrets, tokens, or repository content: field values are the same sanitized identifiers and descriptive error strings the rest of the runner already uses (for example `codex.ClassifiedFailure` deliberately excludes raw provider text), and Docker/sandbox errors carry only the subprocess's own descriptive message, never its stderr, since that stream can include container output or workspace-derived paths. As a defense-in-depth backstop rather than the primary control, `runlog` also redacts any field whose name looks like a credential (matching `token`, `secret`, `password`, `credential`, `authoriz`, `key`, `bearer`, `jwt`, `cookie`, `session`, `signature`, or `signed_url` case-insensitively) as `"[redacted]"` regardless of its value, recurses into nested map values so a credential cannot hide a level down, and separately redacts any string value shaped like a bearer token or a JWT even under an unmatched field name.

The file rotates once it would grow past 5 MiB: the current file is renamed to `runner.log.1` (shifting any existing `runner.log.1`/`.2`/`.3` down one generation and dropping the oldest), and a fresh `runner.log` is opened. Up to three rotated generations are kept alongside the current file, so the log's total footprint under `<state-dir>/logs` is bounded to at most four files of roughly 5 MiB each. A logging failure (a full disk, a permission problem) is dropped rather than interrupting supervision or an attempt; the log is a diagnostic aid, not the attempt's record of truth, which stays the server's attempt/event timeline and the local attempt journal.

This log is local and installed-runner-only. It does not change what the server stores about an attempt or what the run page shows; surfacing a classified attempt failure on the run page's timeline is server-side work tracked separately (see `ianrodrigues/shipmunk-tasks#95`).
