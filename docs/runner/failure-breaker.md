# Runner-classified failure breaker

`run` (continuous mode) stops polling once an attempt ends the same runner-classified way three times in a row, instead of retrying forever against a defect in the runner itself: `Runner stopped polling after 3 consecutive runner-classified failures (last reason: ...)`, pointing at the runner log for the full history. `run --once` still reports a single such failure but never applies the bound.

An attempt is runner-classified only when it points at the runner, not at the queued work, the server, or the network: `malformed_output`, `missing_result`, `invalid_result`, and `invalid_output_schema` (the executor could not produce or was rejected for a structured result the contract expects), or a cleanup that could not be confirmed for a reason other than a refused stopped acknowledgement, a control-plane HTTP error, or a network error. Those three excluded causes are server-side or transport conditions: counting them would trip the breaker on a flaky connection or a server outage instead of an actual runner defect. A provider-classified failure (for example `auth_expired` or `rate_limited`) and an idle poll (no eligible queued work) are not runner-classified either.

The consecutive count only resets when an attempt is delivered and is not runner-classified; an idle poll or a non-runner-classified error leaves it untouched, so a run of idle polls between two runner-classified failures cannot hide the streak.

The count lives only in the running process's memory: it is not persisted to the attempt journal or anywhere on disk, so any restart — an operator relaunch, a supervising wrapper reacting to the process's non-zero exit code, or a host reboot — resets it to zero. The breaker therefore only catches a defect that repeats three times within one continuous run, not one spread across separate launches.

A cleanup failure that is safe to retry in-process backs off and retries on the next poll, after printing the same condition message an operator would see if supervision stopped there. Two causes never retry in-process: a refused stopped acknowledgement, because each reconcile attempt against it would itself advance the server's own three-refusal settle count (see the README's description of `run`'s recovery) and could exhaust that separate bound in seconds instead of requiring the operator relaunches it is meant to require; and an uncertain sandbox create on a reserved name (`sandbox.ErrCreateUncertain`), because it recurs identically on every poll until an operator or the original watchdog resolves it, so retrying would only spin.

A retried cleanup failure caused by a control-plane HTTP error or a network error is exactly the kind the breaker above never counts, so without a check it would retry forever at a fixed cadence and flood stderr with the same line for the whole length of an outage. The supervised loop instead prints that condition in full only the first time, then a periodic "Runner is still failing, N attempts." line while the identical condition repeats, and the retry pause itself doubles on each repeat — from the same base pause the idle poll uses — up to a fixed cap, so a long outage settles into an infrequent, bounded cadence instead of a flood. A delivered attempt or a successful idle poll (either is proof the transport recovered) resets both the pause and the message back to the base cadence and the full condition line. The structured runner log still records every underlying failure event (`claim_failed`, `cleanup_unconfirmed`, and so on) regardless of how the stderr line is paced; see [runner event log](logging.md).

When the third consecutive runner-classified failure is itself a delivered attempt (not an idle poll or a cleanup failure), the loop prints only the breaker line and skips that attempt's usual stdout outcome line, since the bound check runs before the outcome is reported.
