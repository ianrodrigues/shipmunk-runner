# Release packaging and application pins

`php tools/package.php dist v0.1.0-alpha.1` creates a deterministic, uncompressed USTAR package using the shared standalone `PackageBuilder`. Paths are sorted, modes are fixed at 0600, UID/GID and timestamps are zero, and only explicitly selected runtime assets plus regular PHP files under `runner/src` are included. The archive excludes tests, source-control history, application files, setup downloads, credentials, dependencies and generated output. Its size is bounded to 2 MiB, with individual files bounded to 256 KiB. The runtime license is included.

`runner-release.json` contains `version`, the exact public asset `url`, the archive `sha256`, and every included filename's SHA-256 digest. `SHA256SUMS` binds the archive and JSON manifest. The package is independent of Git metadata and source timestamps. The installer validates the complete archive before any extraction, including canonical regular-file headers, a closed path manifest, per-file hashes, zero padding and the exact end marker. Installation creates files exclusively in private staging and rejects unsafe ownership, links or altered existing releases.

The GitHub release workflow listens to `release: published`, which covers stable releases and prereleases, including publication from a draft. Trusted release checks and upload jobs use the existing `github-runner-01` self-hosted Linux runner. Pull request jobs from forks are skipped rather than routed to a hosted fallback; only reviewed internal branches execute on the private runner. The workflow checks the release commit before an upload job rebuilds the package from that same commit. The release tag supplies the package version and must be a valid semantic version prefixed with `v`; no separate version-file edit is needed. `VERSION` is only the default for local packaging when no explicit version is supplied. Release assets are never overwritten with different bytes. The upload step verifies GitHub's recorded SHA-256 digest for every asset, and retries reuse matching assets. Partial uploads can be completed by rerunning the failed job.

After a release succeeds, the application maintainer downloads `runner-release.json`, verifies the published archive and checksums, and commits the exact manifest into `resources/runner-release.json`. The bootstrap uses that reviewed version, URL and digest. Creating a newer runner release does not silently upgrade applications or existing execution hosts. A missing or unavailable pinned release fails setup; it does not fall back to a moving branch or an unverified package.

The initial snapshot retains the `runner/` prefix and the fixture container paths so its existing standalone tests and Docker contexts remain unchanged. `source-snapshot.json` is provenance for the extraction, not a release signature or live compatibility result.

References: [GitHub release workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release), [release asset digests](https://docs.github.com/en/rest/releases/assets#get-a-release-asset), and [GitHub CLI upload behavior](https://cli.github.com/manual/gh_release_upload).
