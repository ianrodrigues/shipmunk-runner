# Codex runtime compatibility

The runner pins **Codex CLI 0.154.0**. It invokes the official `codex exec` process; it does not implement an OpenAI API client or automatically fall back to API-key billing. Native authentication uses the protected assigned profile and the existing `subscription` wire value. Version inspection, current ChatGPT login mode and a small authenticated preflight precede repository work.

## Execution boundary

Codex runs in a credential-only container. A bundled stdio MCP server exposes a mode-fixed tool set, chosen once from a required launch argument (`review` or `repository`; any other value, including an absent one, exits non-zero rather than defaulting) and never changed for the life of that process. Implement and fix runs get only `repository_command`; review runs get only `review_list`, `review_search`, `review_read` and `review_diff`, and never see or can invoke `repository_command`. Both the launch argument and the transport's mount/mediator selection are derived from the same `sources.baselinePath() != ""` value in `internal/codex/executor.go` and `internal/codex/transport.go`, so the tool surface offered and the boundary actually enforced cannot diverge. Every tool's bounded local request file is handled by the trusted host supervisor, which checks the active lease before mediating it. The credential container can evaluate Code Mode JavaScript in the restricted V8 context described below; that context has no direct filesystem, process or network APIs.

Repository commands run in a separate, non-root, network-disabled container with no profile, host workspace, control-plane token or Docker socket mounted, and execute only there. Review's `/baseline` and `/workspace` mounts in that same container are both read-only end to end; nothing in review mode can write source, run a shell, install dependencies or execute repository hooks or tests. That container exists for defense in depth (isolation, cleanup and resource limits stay identical to implement and fix); the review tools themselves never exec into it or run a shell there. Instead, `internal/codex/review_mediation.go` loads the two authorized snapshots once, host-side, into memory through the same validated snapshot reader used for trusted patch collection, and every operation resolves against those in-memory maps only. A request path can therefore never reach the filesystem again: traversal, absolute-path and symlink-escape strings simply fail to match any entry, and a snapshot containing a symlink, hard link or special file fails to load at all, ending the attempt rather than serving partial data.

Review's bounded operations and their bindings, all enforced by the runtime rather than requested by the prompt:

- `review_list(snapshot, path, offset)` lists the immediate entries of a directory (`baseline` or `workspace`; `path: ""` is the root), capped at 500 entries and at the output byte budget, whichever is hit first, with an explicit truncation marker naming the next `offset` so a large directory stays listable across repeated calls rather than failing outright.
- `review_search(snapshot, path, query)` finds a literal substring across a snapshot's text files, capped at 200 matches with a 300-byte snippet per line and an explicit truncation marker. It streams each file line by line instead of materializing it, skips (and marks truncated) any single file over 16 MiB (`MaxReviewScanBytes`), and stops once 16 MiB has been scanned in aggregate.
- `review_read(snapshot, path, start_line, line_count)` streams to the requested window instead of splitting the whole file into lines first, so a small read near the top of a large file costs roughly the size of that window, not the file. It refuses binary content and distinguishes, in the response text, a real output-budget truncation from the ordinary case of more lines existing beyond the requested window (only the former sets the machine-readable `truncated` flag).
- `review_diff(path)` returns the changed-file list (`path: ""`) or a bounded unified diff for one path between the two snapshots, again with an explicit truncation marker if it exceeds the output budget. The per-path diff is served from a map built once by splitting the full diff into sections keyed by the independently verified changed-file paths, not by searching the diff text for a path's header: a reviewed file's own content can never forge another file's section, because every content line in a unified diff body carries a mandatory space/`+`/`-` prefix that a bare `diff --git a/<path> b/<path>` header line can never carry.

Every response is capped at 48 KiB of raw output (`MaxReviewOutputBytes`) inside a 64 KiB response envelope (`MaxReviewResponseBytes`), and that envelope budget is enforced on the JSON-encoded size, not the raw byte count: a string dense in quotes, backslashes or control characters expands once escaped, and a naive raw-byte budget would let such content fail closed with no output at all instead of a bounded, truncated one. The attempt's whole review-request budget reuses the same `max_turns`-derived count already enforced for repository commands. A request whose fence or sequence does not match the current attempt, or that arrives after the mediator is sealed, is rejected outright; an ordinary business rejection such as an unknown or unsafe path comes back as a normal `ok:false` result so one mistaken argument does not end the attempt. See [RT-03](../runtime/RT-03.md) for the live sandbox and credential-isolation scenario these bounds are validated against; this section does not duplicate it.

**Known limitation.** `review_diff` computes its diff once per attempt and caches the result, including a failure: a change set over `MaxChangedFiles` (200) or a diff over `MaxPatchBytes` (1 MiB) makes `review_diff` report "diff is unavailable" for the rest of the attempt, and the diff is currently generated twice internally (once directly, once again inside the shared verification helper) for that one-time computation. Splitting a purpose-built single-generation path with review-specific limits and a truncation marker, instead of reusing the exact patch-artifact limits, is the proposed fix; it is not implemented yet.

**Allowed source-data sharing boundary.** Only bytes physically present in the two authorized review snapshots can ever be returned by these tools, bounded and possibly truncated as above — nothing else on the host or in any container is reachable through this tool surface, regardless of the path string supplied. Source and instruction file contents, including text that looks like an instruction to the model, are always returned as inert data: the mediator never parses or executes them, only echoes bounded snippets. This is not general data-loss prevention: it does not inspect returned bytes for secrets, does not redact patterns, and offers no guarantee beyond "no data outside the two authorized snapshots is reachable." Do not present it as content-based DLP.

The native process starts in `/empty`, ignores user configuration and rules, disables ambient AGENTS discovery, and receives approved dashboard and hash-checked trusted AGENTS instructions explicitly. Candidate `.codex`, hooks, MCP, skills and AGENTS files remain repository data. Native environment variables come from a clean allowlist. No ambient API keys, provider URLs, home directories or proxy settings are inherited.

The native permission profile grants read-only filesystem access and denies `/profile` and `/bridge` to model-invoked filesystem tools. Global approvals remain `never`; only the operator-owned MCP repository tool is explicitly approved. Shell execution, unified execution, optional code mode, plugins, hooks, apps, computer/browser tools, images, goals, memory, multi-agent work and skill discovery are disabled. Bundled runtime instructions belong to the pinned trusted image.

The bundled Code Mode host is enabled for models whose pinned metadata requires `code_mode_only`, including `gpt-5.6-sol`. The optional `code_mode` feature remains disabled. The host evaluates JavaScript in an isolated V8 context: it has no filesystem, process or network globals, and rejects static and dynamic imports. Nested tool calls still pass through the same registered tools and permission checks; enabling the host does not enable shell execution or grant filesystem access.

**Local tools are not all absent.** The pinned runtime still advertises `apply_patch` and MCP discovery tools. Offline forced-tool probes demonstrate denied credential-file add, update and delete operations. Ordinary Docker restrictions also prevent the runtime's nested namespace helper from launching. This fail-closed behavior is part of the tested configuration; do not enable privileged containers, relax seccomp, enable local shell tools or change the permission profile without repeating boundary validation.

Each attempt records deterministic container identities before starting them. Independent host watchdogs cover the native, repository and diff-collector containers. Watchdog children close inherited sibling renewal channels so parent death is detected promptly. A durable profile execution marker spans execution and cleanup; uncertain cleanup retains exclusion and prevents stopped acknowledgement until recovery confirms isolation. Repository code and native account refresh never share a profile concurrently.

Custom repository images must provide Git, GNU find and GNU tar supporting `--format=pax`, `--null`, `--verbatim-files-from`, `--no-recursion` and `--pax-option`. BusyBox tar is insufficient. The bundled native image supplies these tools.

## Inputs, output and sessions

The existing source convention is one head snapshot, or two snapshots ordered base then head. Git archive wrappers are removed only when their suffix matches the supplied revision. Bounded PAX `comment` and `path` records are supported; links, special files and unsupported metadata are rejected, and executable modes are retained without group or world permissions. Commands start in `/workspace` at the head; `/baseline` supplies the base when present. Approved instructions come from the separate version-1 bundle. Configured `max_turns` is enforced conservatively as a maximum number of repository tool calls because this pinned `exec` interface has no general `--max-turns` flag. Repository commands have a 10-second host-side deadline; the MCP bridge waits up to 30 seconds for the response; the claim deadline and renewable lease bound the whole attempt. Repository network remains disabled, including when effective configuration requests restricted network access; restricted egress is not yet implemented.

Native JSONL is limited to 2 MiB overall, 64 KiB per line and 10,000 events. The final model response contains only summary, outcome, findings and tests. Run identity, attempt identity, fence, usage and uploaded artifact references are derived outside the model response. The server revalidates the normalized v1 result and events. Raw reasoning, command output and provider diagnostics are not copied into progress events. Unknown usage is null; no cost is invented.

The generation schema gives every enum an explicit string type and leaves finding paths as bounded strings. Path syntax is enforced by the result parser: absolute paths, parent traversal, backslashes and control characters below U+0020 are rejected before a result can be published. The pinned CLI fixture verifies the schema sent to its loopback provider and passes an unsafe returned path through the production parser. This schema simplification is compatibility hardening, not evidence of a particular live backend rejection.

Authenticated preflight requires a thread start followed by a turn start before successful work, and uses the same item lifecycle validation as execution. A successful terminal requires every tracked item to be complete, a zero process exit code and an exact final `SHIPMUNK_AUTH_OK` message. Failure records can arrive before a turn starts, and a failed terminal can end with active items; the sanitized failure reason is retained after the complete stream passes validation.

Review runs return findings without collecting a patch from their disposable workspace. Test and build commands may create caches or generated files; those side effects are discarded at cleanup. A review result cannot publish a change artifact. Implementation and repair runs still collect and validate their filesystem changes against the supplied source snapshot.

Review has no reproduction or test execution capability at all: its prompt states that test evidence is unavailable in this mode, and the runner rejects any review result whose `tests[]` entries report a status other than the existing `not_run` marker, so an executed-looking test result can never be published for a review run. Trusted, separately provenanced test receipts are a future extension of the result contract, not yet implemented.

## Review charter and structured evidence

Every review run is bound to [the trusted review charter](../review-charter.md), version `1`, embedded in the runner binary from `internal/codex/charter.md` (`internal/codex/charter.go` carries `ReviewCharterVersion`) and injected into the developer instructions ahead of the approved repository configuration. The charter asks for declared-versus-observed comparison, the contracts and interfaces the change touches, security and maintenance consequences, test adequacy under the no-execution constraint above, and a self-refutation pass before any finding is reported; it carries no criticism quota and grants no merge authority. Alongside the charter text, the prompt is given this attempt's two real snapshot SHAs (`diff_base_sha` and `head_sha` from the claim manifest, labeled baseline and workspace) and the exact planned changed-file list, computed the same way `review_diff` computes its own changed-file list: both snapshots are loaded and diffed once via `buildReviewEvidence`, independently of whether the model ever calls a review tool, so the prompt's list and the coverage set normalizeExecution checks against are always the same computation. `review_list` and `review_read` responses additionally carry a `snapshot_sha` field naming the real SHA of whichever snapshot was read, so the model can cite an identity it was actually given rather than inventing one.

When outcome is `findings` or `no_findings` the result also carries `charter_version`, `coverage` (`files`, each `reviewed` or `unreviewed` with a reason required only when unreviewed, plus `context_gaps`) and `verification_state` (`"none"` for charter version 1: no execution receipt exists), and may carry up to 20 `questions`; `incomplete` may carry `coverage` alone, and `changes_proposed`/`needs_input` forbid all four. A finding is `category`/`severity`/`relation`/`scenario`/`consequence`/`action`/`explanation` plus one to five `evidence` citations of `{snapshot, path, line_start, line_end}` and an optional presentation-only `anchor`; the retired top-level `path`/`line`/`side`/free-text `evidence` are gone with no compatibility shape behind them. A question is `topic`/`question`/`why_material` plus optional evidence and carries no severity, so an unanswered question can never be presented as a finding of invented weight.

`normalizeExecution` re-validates a review result against the two snapshots it actually holds, independently of the model's own self-refutation pass and independently of the server's own acceptance checks against its frozen changed-file inventory: every evidence `snapshot` must equal the attempt's real baseline or head SHA; every evidence `path` must exist in that same snapshot's content with `line_end` within its actual line count; `coverage.files` must equal the planned changed-file set exactly, with no extra, missing or duplicate path; an `introduced` or `modified` finding must cite at least one head-snapshot path inside that changed-file set; and `no_findings` is rejected outright if any file is unreviewed or any context gap is recorded, since a known omission or an interrupted review can never be presented as a clean result. These checks are sanitized, explicit failures, never a silent drop of a malformed field. The wire shape is mirrored byte for byte from the server's `contracts/v1/result.schema.json` into `internal/protocol`, including its `$ref`/`$defs` structure, which the runner's schema engine now resolves; `internal/protocol/schema.go` additionally enforces the one rule JSON Schema cannot express on its own, an evidence citation's `line_end` at or above its `line_start`, the same way the server's own boundary check does.

Repository changes are collected from a frozen, bounded tmpfs snapshot using a separate collector. The original source and Git metadata are protected from repository commands, so rewriting repository history cannot hide edits. Patch artifacts contain the diff, verified before/after hashes and modes, tests and base revision in the server’s JSON envelope. Code-change runs must pin `diff_base_sha` and `head_sha` to the same original revision; review runs cannot publish patches. At most 200 changed files are accepted.

Malformed/truncated output, missing results, invalid structured results, process failure, expired authentication, rate limits and unavailable approvals have distinct sanitized failure reasons. Backend `model_not_found` and `invalid_json_schema` codes become `model_unavailable` and `invalid_output_schema`. The pinned CLI can embed the backend JSON error body inside its message; the parser accepts only one strict object envelope with a known error code. Malformed JSON, duplicate keys, unknown codes and unrecognized provider wording remain a generic process failure. A failed runtime cannot emit a successful patch result. The runner records a fixed failure stage (version inspection, account verification, authenticated preflight, execution or result validation), a closed reason code and the native process exit code in one progress event and the result summary. Unknown exit codes remain unavailable; raw provider text is never included. Terminal completion feedback follows accepted result delivery, confirmed cleanup and stopped acknowledgement; `--once` returns a nonzero exit code for incomplete or approval-blocked work.

Session records live outside native and repository mounts and are looked up by explicit run ID. Compatibility binds the provider version, profile and credential reference, repository revisions, approved configuration, instruction and source artifacts and saved task context. A compatible record uses an explicit UUID; mismatches reconstruct a fresh session. No invocation uses `--last` or searches globally recent history. A retry starts with the supplied original source snapshots; resumed context must re-read that filesystem instead of assuming previous edits survived.

## Verification and limits

`CodexEventParserTest.php` uses labeled synthetic JSONL fixtures. `CodexDriverTest.php` simulates the native transport. Server contract and API tests validate the actual driver output, patch upload, completion and stopped acknowledgement. Docker transport tests use a synthetic native program with real Linux container boundaries. The native boundary fixture uses the actual pinned CLI and a loopback mock provider inside a network-disabled container to force tool calls and backend rejections. Actual CLI rejection output passes through the production parser to verify known codes and unknown-code fallback without exposing provider messages. Its synthetic API credentials never leave the fixture and are not a production authentication mode. A synthetic model catalog forces `code_mode_only` without an account or cached provider metadata. Host-disabled failure, denied imports and I/O globals, protected-file patch rejection, and successful nested MCP mediation are checked under the production container resource limits.

The synthetic supervisor integration scenarios exercise the complete container lifecycle, cancellation of repository children and parent-death watchdog cleanup. Fixture coverage and final integrated quality gates must be reported separately.

These checks do not establish live ChatGPT subscription compatibility, refresh, expiry, reconnect or release readiness. Execute [the designated-account scenario](../runtime/RT-02.md) and [configuration/credential provenance checks](../runtime/RT-03.md) on the intended Linux host. Both scenarios remain `not_run` until completed. A reported local login/readiness pass is narrower than the full scenario.

Official mechanisms were checked against [non-interactive execution](https://developers.openai.com/codex/noninteractive/), [managed account authentication](https://learn.chatgpt.com/docs/auth/ci-cd-auth), [MCP tool approval](https://learn.chatgpt.com/docs/extend/mcp) and the [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). Exact flags and security behavior are additionally exercised against the pinned executable; current documentation alone is not proof of compatibility.
