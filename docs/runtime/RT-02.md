# Live Codex subscription lifecycle

Use a designated subscription account, a dedicated Linux runner host, a connected Shipmunk control plane and an administrator-created `codex` profile with `auth_mode=subscription` and `runtime_version=0.154.0`. Give the operator a mode-0600 token file with the `runner:profiles` ability for that profile's assigned runner. Do not use personal account caches.

The `shipmunk-profile` and `shipmunk-runner` commands below are the Go binaries: extract `bin/shipmunk-profile` and `bin/shipmunk-runner` from the application's pinned release archive (see [release packaging](../releases.md)), or build them locally with `go run ./cmd/shipmunk-package . dist vX.Y.Z` and extract them from the matching archive under `dist/`. They accept the same flags as the retired PHP commands of the same name.

## Login and status

Build the pinned credential-only image on the runner host:

```sh
docker build --tag shipmunk-profiles:local --file runner/containers/Dockerfile .
```

Set the following non-secret identifiers for the designated environment. The profile ID and each operation ID must be canonical lowercase ULIDs. Generate a new operation ID for each login, probe or disconnect; retry an interrupted operation with its original ID to recover its journal. Recovery can finish successfully and then exit nonzero because that identifier is already completed. Check the sanitized profile health after recovery and use a new operation ID for the next login, probe or disconnect.

```sh
SHIPMUNK_URL=https://shipmunk.example
SHIPMUNK_PROFILE_ID=replace-with-profile-ulid
SHIPMUNK_OPERATION_ID=replace-with-operation-ulid
./shipmunk-profile \
  --base-url="$SHIPMUNK_URL" \
  --token-file=/etc/shipmunk/profiles.token \
  --profiles-dir=/var/lib/shipmunk-profiles \
  --image=shipmunk-profiles:local \
  --profile="$SHIPMUNK_PROFILE_ID" \
  --operation=login \
  --operation-id="$SHIPMUNK_OPERATION_ID"
```

Run as the dedicated non-root runner account; pre-create its protected profile root with mode 0700. Complete the official native login in the terminal. Select the designated subscription account. Do not capture the terminal login code or URL in screenshots, task evidence or centralized logs. The workflow sends a small fixed authentication prompt using that subscription after login; it does not execute repository code. Expect sanitized final health `ready`, then repeat the command using `--operation=probe` and a new operation ID.

## Required assertions

1. Record exact image digest and runtime version. Verify the status identifies the expected subscription account mode; an API-key or Console account must not become `ready`.
2. Start competing login/probe operations. Only one may own the profile. Queue execution while login holds it: execution must wait. Reconnect must not overwrite an in-use home.
3. Revoke or expire the designated session using provider-supported account controls. Probe and run a minimal private-repository task through `--driver=codex`. Authentication failure must stop work with a sanitized reason and no alternate billing mode or profile fallback. Reconnect with a fresh native login and repeat.
4. During login, disconnect the profile through the administrator API. The credential container must stop, a late success must not restore readiness, and new claims must remain disabled. Run the operator command with `--operation=disconnect` and a new operation ID to acknowledge local removal. Administrator reconnect must wait for cleanup.
5. Kill the operator process during login. Confirm its watchdog terminates the credential container and that rerunning the operator command reconciles the durable journal before starting another operation. Repeat with a dropped completion response.
6. Inspect only metadata and permissions: no credential bytes or raw status output may enter the application database, audit entries, artifacts or logs. Execute [RT-03](RT-03.md) for the cross-profile and repository-isolation assertions.
7. Exercise real execution, automatic native refresh, session reuse and expired-session recovery using the explicit Codex driver below. A local login/status pass alone is not completion of this scenario.

## Execution and compatible sessions

Use a separate execution token assigned to the same runner, with the `runner:poll`, `runner:events` and `runner:results` abilities. Prepare one designated private-repository run whose profile is the connected Codex profile and whose source and trusted-instruction artifacts have been staged by the control plane. Use canonical, mode-0700 directories owned by the dedicated non-root runner account. Do not use a personal checkout or credential cache.

```sh
./shipmunk-runner \
  --base-url="$SHIPMUNK_URL" \
  --token-file=/etc/shipmunk/runner.token \
  --state-dir=/var/lib/shipmunk-runner \
  --driver=codex \
  --profiles-dir=/var/lib/shipmunk-profiles \
  --image=shipmunk-profiles:local \
  --repository-image=shipmunk-profiles:local \
  --once
```

Confirm a real claim was processed; an idle `--once` exit proves no execution. Record the run/attempt IDs, normalized outcome, stopped acknowledgement and absence of attempt containers and workspace volumes. Repeat with a code-change run to check the uploaded patch envelope without publishing a GitHub change. Confirm native/repository separation using RT-03.

For a compatible retry of the same run, verify that the exact recorded session is selected and that its context re-reads the supplied original source snapshots. Repeat after changing the approved configuration or credential reference: the old session must not be reused. Exercise account expiry and a provider-supported refresh, then reconnect after revocation and repeat the minimal run. Record each observation independently; synthetic tests and an idle or successful login command do not satisfy these assertions.

Record pass/fail per assertion, sanitized reasons and designated resource IDs. Leave this scenario `not_run` until executed; report partial results explicitly. Product disconnect removes local access but does not itself prove remote provider revocation.
